## 二、和原计划的三处差异

### 1. 文件数从 44 变成 2000+，因为把 emoji 从「24 个图标」改成了「可替换的图标库」

`docs/art/卡面美术资源清单.md` 当时的结论是「真正需要准备的只有 3 类、约 44 个文件」，其中分类图标 24 个。

这个数字基于一个判断：**分类图标是一套固定图标**。但 PRD 3.1.2 定的是 8 个分类，而 8 个分类里的「吃」「乐」「情」根本没法用单个图标表达——一顿火锅和一杯咖啡都在「吃」里。

所以改成两层：分类名固定（8 个），**图标从该类候选里选**。492 个精选就是这个候选池。代价是体积，收益是「吃」下面有 28 个图标可以挑，而不是被迫用一个汉堡代表所有吃饭。

### 2. 用了 3D 版，所以只能是 PNG 不是 SVG

原清单要求 SVG + `currentColor`，好处是换主题不用重导。

但微软 Fluent Emoji 的 3D 版**只有位图**，矢量只有 Flat / Color 两套。选 3D 就是选 PNG，颜色写死在像素里，不能跟随主题变色。

补偿办法：图标本身是彩色立体物，外框底色（`#F6F4EF`）和选中态颜色仍由代码控制，视觉上不会突兀。如果哪天觉得 3D 太重，`gen-textures.js` 同目录可以再拉 Flat 那一套（8.7 MB 解压，小得多）。

### 3. 品牌标没做，只做了品牌色

原清单 P0 是「17 个银行/品牌标 SVG」，来源优先 Simple Icons。

没做的原因有两个：一是本机网络只通了 npm 镜像和 codeload，Simple Icons 和各家品牌中心都超时；二是更重要的——**卡面由代码绘制，Logo 是唯一需要图片的那块，而它恰好是法律风险最高的一块**。

替代方案已经在 `brands.json` 里落地：每个品牌带 `en`（CMB / CCB / ALIPAY / WECHAT）和 `short`（招行 / 建行 / 上行），卡面用文字标。这版文字标在 `cards/*.svg` 里可以直接看效果，零法律风险，且和低饱和调性更配。

## 三、三个技术判断

**1. 纹理是程序化生成的，不是找来的。**
固定随机种子 + 手写 PNG 编码器，重跑逐字节相同。好处是不依赖任何素材站，坏处是 `tex-grain.png` 压不到 15 KB —— 纯随机噪点熵太高，PNG 压缩率有物理下限，50 KB 就是它的下界。三张合计 122 KB，对 App 无影响。

**2. 同品牌多账户靠 `variant` 区分，不另配一套色。**
建行 5044 / 0565、招行三张卡，色值完全一样的话在列表里会糊成一片。`variant: 0/1/2` 对应原色 / 压暗 14% / 提亮 16%，视觉上能分开，数据上仍是一个品牌。

**3. 3D Emoji 是从 npm 包抠出来的，不是从 GitHub 仓库下的。**
`microsoft/fluentui-emoji` 整包超过 1 GB（四种风格 × 全语言 × 多尺寸），而 3D PNG 全部 base64 内嵌在 `fluent-emoji@0.1.2` 的单个 `index.js` 里，50 MB 拿全 1545 个。`_build/fetch-fluent3d.js` 已实测可重跑。

## 四、还没定的三件事

1. **品牌标要不要真 Logo**。现在纯文字。要真 Logo 得另找 17 个矢量文件，且上架有驳回风险。
2. **492 个精选是否全量进包**。15.2 MB；只放常用的 40 个约 1.3 MB，但换图标时没得选。
3. **卡面比例**。现在 148×93（1.586，ISO 标准）；原型是 148×92（1.609）。差 1.5%，肉眼无感，要不要统一。

这三条都不阻塞骨架搭建——`brands.json` 和 `categories.json` 已经把数据形状定死了，换图标、换比例都只是改参数。
