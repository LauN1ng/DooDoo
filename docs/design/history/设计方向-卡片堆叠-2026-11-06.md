## 一、本轮四个决定

1. **卡堆 = 真叠层，形态取「散叠」**：前卡压住 3 张后卡，后卡从底边露出纸边（10pt 一层，共 30pt），并左右错位 + 轻微旋转。不是"旁边露一条边"，也不是"对齐的竖叠"。
2. **左右必须留白**：后层不能顶到屏幕边缘。做法是**先内缩再散开**——后层的 `left/right` 比前卡大 9~12pt，旋转与错位消耗掉一部分后仍留 ≥8pt。
3. **便签保留**（用户原话「保留这个」）：`较上月 ↘12.4%` 用 −3° 便签压在卡片右上角，替换页头胶囊。
4. **移除卡片底部的重复入口**（已执行，见第五节）。

## 二、为什么前三版被否决

| 版本 | 做法 | 问题 | 结论 |
|---|---|---|---|
| v1 | 横向卡盒，左侧 peek 10~12pt | 露出的是一条竖边，占屏宽 3%；**看不见** | 废弃 |
| v2 | 底部 3pt 纸叠边 ×2 | 3pt 与卡片投影混在一起，**与基线无法区分** | 废弃 |
| v3 | 竖叠 3 层，12pt 一层，四角对齐 | 能读出"一叠"，但和后卡加阴影几乎同义，**偏静、偏死** | 保留为对照，不作最终 |

用户的判断是对的：**前两版不是"堆叠"，而是"给卡片加了一条边"**。堆叠感需要三个条件同时成立——纸边**厚度够**（10pt 起）、**层数够**（3 层起）、层间**有明确分隔线**（不能只靠投影渐变）。

## 三、采用方案：散叠（S2）

原型：`design/current/stack-variants.html`，顶部 chip 切换，四个状态都能横向拖动，默认选中「散叠卡堆」。

### 3.1 几何参数（最终值，已实测）

| 项 | 前卡 lay0 | 后层 1 | 后层 2 | 后层 3 |
|---|---|---|---|---|
| `left/right` | 16pt | 26pt | 25pt | 28pt |
| `bottom`（决定露出厚度） | 30pt | 20pt | 10pt | 0 |
| 静止旋转 | — | −1.0° | +0.9° | −1.3° |
| 静止横向错位 | — | −5pt | +4pt | −4pt |
| 拖动附加旋转 | — | −1.0° | +1.2° | −1.4° |
| 拖动附加错位 | — | −2pt | +2pt | −2pt |
| 拖动上掀 lift | — | 4pt | 3pt | 2pt |

层间分隔线（后层专用，缺一不可）：

```css
box-shadow:
  0 1px 0 rgba(29,28,26,.10),          /* 底边一条硬线 —— 这是"层"的来源 */
  0 4px 8px rgba(29,28,26,.05),        /* 极窄外投影，只做分离，不做重量 */
  inset 0 0 0 1px rgba(29,28,26,.11);  /* 描边保证白卡在白底上也读得出 */
```

前卡投影只能窄：`0 3px 5px rgba(29,28,26,.05)`。**放大投影会把后层纸边糊成一片灰**，这是 v3 踩过的坑。

### 3.2 留白规则（本轮新增，最重要）

旋转会让矩形角部横向外扩。实测外扩量约等于 **卡片高度 × sinθ**（不是半高 × sinθ，因为旋转原点不在几何中心），本项目卡片高约 650pt，**每 1° ≈ 11.3pt**。

所以每层的最小内缩量必须满足：

```
left_inner ≥ h · sin(θ_max) + |x| + gap_wanted
```

| 层 | 旋转 | 错位 | 理论外扩 | 内缩 | 实测左留白 | 实测右留白 |
|---|---|---|---|---|---|---|
| lay1 | 1.0° | −5 | 16.3 | 26 | **10.0** | 31.0 |
| lay2 | 0.9° | +4 | 14.2 | 25 | 29.0 | **10.9** |
| lay3 | 1.3° | −4 | 18.7 | 28 | **9.3** | 32.0 |
| 前卡 | 0° | 0 | 0 | 16 | 16.0 | 16.0 |

**拖动中间态（dx=−90、散开进度 0.6）实测**：lay1 左 15.4 / lay3 左 17.6，均未越界。前卡飞出屏幕属预期（被 `overflow:hidden` 裁掉）。

结论：**静止时左右最小留白 9.3pt，拖动中最小 15.4pt，任何时刻不顶边**。这个 9~10pt 就是"左右要有一点留白"的量化落地值——低于 6pt 肉眼就读成贴边。

### 3.3 视觉要点

- 后层的**内容全部 `opacity:0`**，只留白纸面。否则左右错位后，"NOV"、"−¥32.00" 会从缝里漏出来，很脏。
- 后层颜色必须是**纯白 + 描边**，不能用 `#FCFAF6` 之类近底色（与页面底 `#F7F5F1` 差 1.5%，等于没画）。
- 后层宽度比前卡窄 20~24pt，这是刻意的：散开后如果与前卡等宽，宽出来的部分会顶到屏幕边；略窄反而更像"被压住的一叠"。
- 后卡在卡片**顶部也会露出角**，这是散叠与竖叠最直观的差别，也是"活"的来源。可接受，不要试图裁掉。

### 3.4 3 层 vs 4 层（实测）

原型已加「散叠 4 层」对照，同样的错位规律多压一层。

| 项 | 3 层 | 4 层 |
|---|---|---|
| 后层数 | 3 | 4 |
| 每层露出 | 10pt | 10pt |
| 叠层总厚 | 30pt | 40pt |
| 前卡高度（实测） | **622pt** | **612pt** |
| 后层左右留白 | 9.3 ~ 10.9pt | 9.5 ~ 11.5pt |

**结论：保留 3 层。** 理由是边际收益递减——第 4 层只多给 10pt 厚度（占屏高 1.2%），却让卡片矮 10pt（可见内容少一行流水的空间），而且第 4 层的错位边被前三层的阴影叠着，在真机尺寸下已经数不清是第几层。3 层读成"一叠"，第 4 层只是"更厚一点的边"。

参考图是 4 层，但它展示的是宣传图（放大、无损、无阴影干扰），不构成 4 层的必要证据。

### 3.5 便签（较上月）· 完整规格（v10 定稿）

**形态**：−3° 斜贴的米黄便签，压在卡片**右上角**，替换页头胶囊（v4 起沿用，用户明确「保留这个」）。

```css
.note{
  position:absolute; right:6px; top:-14px; transform:rotate(-3deg);
  background:#FFF7E0; border:1px solid #EFE2BE; border-radius:5px;
  padding:5px 10px; font-size:11px; color:#8A6D2F;
  box-shadow:0 3px 8px rgba(0,0,0,.09); z-index:6; white-space:nowrap;
}
.note s{ text-decoration:none; color:#3B7A44; }   /* 绿 = 下降 */
```

| 项 | 值 |
|---|---|
| 位置 | 卡片右上角，`right:6pt / top:-14pt`（**越出卡顶 16.6pt**，压在上沿） |
| 旋转 | −3°（唯一一处旋转，卡片本身不转） |
| 底 / 边 | `#FFF7E0` / `#EFE2BE` 1px，圆角 5px |
| 文字 | 11px，`#8A6D2F`（标签）+ `#3B7A44`（数值，绿） |
| 投影 | `0 3px 8px rgba(0,0,0,.09)` |
| 显示条件 | **仅「今天」那张卡**（详见下方 R4） |

#### 3.5.1 便签上挪 4pt 的实际意义（有实测）

| 测量项 | 当前值 |
|---|---|
| 便签底边 | y=232.0 |
| 「支出 −¥165.00」顶边 | y=236.0 |
| **两者垂直间隙** | **4.0pt** |
| 便签阴影（`0 3px 8px`）可见下沿 | y≈239 |
| **阴影压住金额的量** | **3 ~ 7pt** |
| 便签越出卡片顶部的量 | 16.6pt |

所以上挪 4pt 不是审美微调，而是**让便签投影不再压在金额数字上**：间隙 4 → 8pt，阴影下沿从 239 回到 235，正好脱开 236 的金额顶边。代价是越界从 16.6 变 20.6pt，距页头 `DooDoo` 标题仍有约 25pt，安全。

更好的替代（未采用，留作备选）：不改位置，把便签阴影改成 `0 2px 4px` 并降不透明度，视觉上同样干净，且不动越界量。

#### 3.5.2 「较上月」的口径（v10 定案）

> 原写法「较上月 ↘ 12.4%」**有两个缺陷**：① 「较上月」没说是哪个时间范围——比的是「上月同一天」「上月整月」还是「上月同期」，读法不唯一；② 便签贴在一张**日**卡上，读者会默认它跟这张纸（今天）有关，而它其实是月度指标。

**口径定为「MTD 同期」**：

| 项 | 定义 |
|---|---|
| 分子 | 本月 1 日至今天的**总支出** |
| 分母 | 上月 1 日至**上月同一天**的**总支出**（同期天数对齐） |
| 结果 | `(分子 − 分母) ÷ 分母 × 100%` |
| 颜色 | 支出下降 → **绿**（涨红跌绿，按方向不按好坏） |
| 算例 | 本月至今 −¥4,382（11/1–11/6）；上月同期 −¥5,002（10/1–10/6）→ `(4382−5002)/5002 = −12.39%` → **↘ 12.4%** |

**为什么不用另外三种口径**：

| 备选 | 问题 |
|---|---|
| 本月至今 vs **上月整月** | 11 月只有 6 天对 10 月 31 天，**必然显示 −80%**。这是日历长度差，不是消费行为差。最常见的错口径 |
| **今天** vs 上月同一天 | 单日噪声极大：一笔 129 元的猫粮就能把百分比翻转 ±20%，12.4% 这种精度是噪声不是信息 |
| 本月日均 vs 上月日均 | 也稳，但要两次除法、解释成本高；「较上月」的日常语义更接近同期总额对比 |

**六条实现规则**：

| # | 规则 | 理由 |
|---|---|---|
| R1 | 口径 = MTD 同期（见上表） | 同天数对比才有意义 |
| R2 | **分母为 0（上月同期没花钱）时改显示绝对额**：便签写「本月 −¥4,382」，不写百分比 | 除零无解；绝对额永远可算 |
| R3 | 文案由「较上月」改为「**本月**」 | 标签要自解释；「较上月」是模糊的月份关系，「本月」是明确的指标名。后面板里再展开同比细节 |
| R4 | **便签只在「今天」那张卡上显示**；往回翻页时隐藏 | 口径是月度的，贴在 11 月 5 日的纸上会被读成「11 月 5 日较上月」。翻页即消失，唯一不会误读的做法 |
| R5 | 数值色：支出下降绿、上升红 | 涨红跌绿，全局统一 |
| R6 | 便签**可点**，点击展开月度面板（支出 / 收入 / 结余 / 日均 / 同比） | 便签是首页唯一的月度指标，必须有去处；否则用户只看到一个百分比，无从判断它意味着多少钱 |

**R6 的补充**：月度面板里要同时给出**绝对额**。基数是几千块时，「↘12.4%」用户算不出等于多少钱；百分比回答「方向和比例」，绝对额回答「多少钱」，两者缺一不可。

### 3.5.3 单日流水过多时怎么处理（v10 定案）

**问题**：真实量级是 331 笔 / 3 个月 ≈ **3.7 笔/天**，但会有极端日（今天 14 笔）。而一屏装不下：

```
卡片高 698pt − padding 44 − 卡头 36 − 分隔线 17 = rows 可视 601pt
每行 64pt（图标 42 + padding 11×2）
⇒ 601 / 64 = 9.4 行，一屏 9 笔，第 10 笔露头
```

**三版实测**（原型 `design/current/day-overflow.html`，14 笔）：

| | A 卡内滚动（现状） | **B 渐隐 + 计数** | C 分类折叠 |
|---|---|---|---|
| 内容总高 / 可视高 | 944 / 604 | 944 / 604 | 944 / **576** |
| 溢出量 | 340pt | 340pt | **368pt（更差）** |
| 底部收尾 | 硬切 | 渐隐软收尾 + 计数行 | 硬切 |
| 用户知道还有内容吗 | 不知道 | 知道，且知道剩 5 笔 | 不知道 |
| 结论 | 否 | **采用** | 否 |

**C 版为什么反而更差**：分组头本身占 64pt，6 个分类 = 6 个头 + 14 个明细 = 944pt，**比不折叠还多 28pt**。「分组头 + 明细」两行才等于原来一行加一个头，折叠没有省空间。而且「情」分组被墨键导航整组盖住。

**B 版的三层结构**：

| 层 | 做法 | 作用 |
|---|---|---|
| ① 软收尾 | rows 底部 34pt `mask-image` 渐隐 | 读成"下面被盖住"而不是"被切断" |
| ② ~~明示余量~~ | ~~固定一行「下面还有 N 笔 · 看全部 ›」~~ | **用户裁定：不加计数行**，只要渐隐 |
| ③ 隐藏滚动条 | `scrollbar-width:none` + `::-webkit-scrollbar{width:0}` | 只留渐隐，不出现系统滚动条——留了就把"纸"读成网页容器 |

> **计数行已否决（用户 2026-11-07：「采纳渐隐，但是不要计数」）**。只留渐隐作为"下面还有"的暗示，不主动报数量。少一个元素、少一处信息冗余，代价是用户不知道确切还剩几笔——这个代价用户已接受。

**B 版的两条硬约束**（三版原型都踩到了，截图才看出来）：

1. **卡片下内边距必须 ≥76pt**。墨键导航浮在卡上（距屏底 52~88pt）、FAB（58~110pt）；内容底 = 卡片底 46 + padding-bottom，必须高于 FAB 顶 110pt ⇒ padding ≥ 64pt。但 FAB 是**圆形**，视觉上缘比几何边界更高，实测 padding 64 时 rows 底正好落在 FAB 顶 110pt 上（间隙 0），最后一行仍被压。取 **76pt** 留 12pt 余量。**这个数会随 tab 栏方案变，tab 栏定案后必须重测**（与 3.2 的留白测量是同一类纪律）。
2. **手势仲裁**：卡内纵向可滚 + 卡堆横向翻页在同一区域。按**首 8pt 位移主轴**判定方向——纵向给滚动、横向给翻卡。不做仲裁的话，翻卡会误触发卡内滚动。

**不做的事**：

- 不做「按分类折叠」（已实测更差）。
- 不做「卡片变高」。层厚是"有几天"的唯一证据，卡片高度一变，露出的 10pt 厚度就跟着变（见 3.2 的 `h·sinθ` 规则），叠层语言直接失效。**卡片高度锁死，超出只能滚。**
- 不做「一键折叠成 3 笔」。那是把信息藏起来，不是解决问题；用户要的是"知道还剩多少 + 能看完"，不是"看不到"。

**SwiftUI 映射**：

```swift
ScrollView {
    LazyVStack(spacing: 0) { ForEach(day.transactions) { TransactionRow($0) } }
}
.scrollIndicators(.hidden)                 // ③ 隐藏系统滚动条
.mask(                                      // ① 底部渐隐
    LinearGradient(stops: [.init(color: .black, location: 0),
                           .init(color: .black, location: 0.95),
                           .init(color: .clear, location: 1)],
                   startPoint: .top, endPoint: .bottom)
```

> **不要加计数行**（用户裁定）。SwiftUI 里若将来需要，正确做法是 `.safeAreaInset(edge: .bottom)` 挂一行，不要塞进 ScrollView 内容里。

**已落地**（`design/current/home-final.html`）：

| 改动 | 值 |
|---|---|
| 便签 | `本月 ↘ 12.4%`，`right:6 / top:-14 / rotate(-3°)`，`#FFF7E0` 底 + `#EFE2BE` 边，数值 `#3B7A44` |
| 便签显示条件 | `day.today` 为真时渲染（DOM 里只有 1 个 `.note`） |
| rows | `overflow-y:auto` + `scrollbar-width:none` + 底部 34pt `mask-image` 渐隐 |
| 计数行 | **无**（用户裁定去掉） |
| 卡片下内边距 | **76pt**（实测 rows 底 122pt，FAB 顶 58pt，间隙 12pt） |
| 手势仲裁 | 首 **8pt** 按位移主轴判定（`axis = |d| > |dy| ? 'x' : 'y'`），纵向给滚动、横向给翻卡；`.deck` 加 `touch-action:pan-y` |

**验证**（tabbit 实测，390×844）：`noteCount=1`、`noteVisible=true`、`rowsClearOfFab=true`、`rowsClearOfNav=true`、`gapRowsToFab=12`、`overflowPx=0`（今天 3 笔不触发渐隐）。

### 3.6 空日卡：保持等厚（已定）

### 3.6 空日卡：保持等厚（已定）

空日卡（没花钱的一天）**不压缩高度**，与有流水的卡等高、露出的叠层厚度一致。

理由：叠层的可信度来自"每层厚度一致"。一旦允许高度差，逐层露出的 10pt 就会忽宽忽窄，读起来是"卡歪了"而不是"一叠卡"。空日卡内部用留白 + 一句 `没花钱的一天 :)` 撑住高度即可，这也符合"把空白留给内容"的既有原则。

## 四、SwiftUI 实现映射

```swift
ZStack(alignment: .bottom) {
  ForEach(visibleCards) { card in            // 只实例化 rel = 0, -1, -2, -3
    let k = -card.rel
    CardView(card)
      .padding(.horizontal, insetX(k))       // 0 → 0, 1 → 10, 2 → 9, 3 → 12
      .padding(.bottom, insetB(k))           // 0 → 30, 1 → 20, 2 → 10, 3 → 0
      .background(
        RoundedRectangle(cornerRadius: 24)
          .fill(.white)
          .overlay(
            RoundedRectangle(cornerRadius: 24)
              .strokeBorder(Color.black.opacity(0.11), lineWidth: 1)
          )
      )
      .rotationEffect(
        .degrees(tilt(k) + dragProgress * fanTilt(k)),   // tilt: -1.0 / +0.9 / -1.3
        anchor: .center
      )
      .offset(x: drift(k) + dragProgress * fanDrift(k))   // -5 / +4 / -4
      .opacity(card.rel <= 0 ? 1 : 0)
      .zIndex(Double(100 - card.rel))
  }
}
```

实现注意：

- **`rotationEffect` 用 `.center` 锚点**，此时水平外扩为 `h/2·sinθ`；网页版因为是绝对定位 + 不同原点，实测更大。SwiftUI 里按 `h·sinθ` 预留更安全。
- 后层内容用 `if card.rel == 0` 关掉，别让它们参与布局和离屏渲染。
- 拖动期间 `transaction(animation: nil)`，settle 时用 `spring(response: 0.34, dampingFraction: 0.86)`。
- 翻页阈值：位移 > 22% 卡宽，或速度 > 0.55。

## 七、边界与风险

1. **外扩是按卡片高度算的**。卡片一变形（空日卡变矮、内容变多、字号放大），`h·sinθ` 就变，留白会失效。实现时把内缩做成常量没问题，但**改卡片高度后必须重跑一次留白测量**。
2. **空日卡的高度差**。没花钱的一天只有一句话。当前实现假定等高；若允许高度差，露出厚度会不齐，散叠的错落感会变成"歪"。
3. **「更早的流水」是异形卡**，混进同一叠会破坏同质性。建议做成封底：不参与叠层，只叠最底一条 44pt 薄条。
4. **底部叠层与 tab / FAB 的层序**。当前 deck 底边距屏幕底 87pt，tab 与 FAB 均在其下，无冲突；卡片下延或 tab 上移时，叠层会第一个被压。
5. **拖动时前卡会飞出屏幕**（`translateX(420px)`），这是对的，但要注意别让后层的错位也跟着线性放大——本方案把 `fx` 收到 ±2pt 就是为了这个。
6. **叠层与"卡片权重三层"的关系**。后卡是 L0（只做材质），不能因为"存在感不够"给它们加深阴影——一加深就又糊成一片。

**为什么后层颜色必须手动指定**：我先写了色相距离算法自动挑，结果第三层选中「平安橙」——因为橙与红的 hue 差 27°、与蓝的差 188°，算法认为它比黑卡（与蓝只差 22°）更"对比"。但视觉上暗橙卡经 `brightness(.74)` 后变成**棕色**，和第一层的红卡同族，读起来是"红卡带了两条不同深浅的描边"。手动打 `stack` 标记最可靠：招商红 → 花呗蓝 → e招贷黑，正好复刻参考图的三层。

### 为什么不用「原地展开」（v4 最重要的一次否决）

上一版把明细列表直接插回资产页里、把卡牌堆换成账户行。用户否掉：**「直接展开会把画面撑大」**。

实测差异：

| 做法 | 信用组 | 储蓄组 | 整页 | 溢出 |
|---|---|---|---|---|
| 原地展开（旧） | 472.5pt | 273.3pt | — | **308pt** |
| **覆盖层（定案）** | 不占资产页高度 | 不占 | **792pt** | **0** |

原地展开等于把一屏的信息量塞进同一屏，必然撑高；覆盖层是**换一屏**，资产页的高度永远不变。这一条同时解释了为什么它和首页叠卡是同一套语言：两者都是「点开一个容器，进到里面」，不是在原地长出来。

### 实测（`account-stack.html` v7，390×844）

| 状态 | 高度 | 溢出 |
|---|---|---|
| 收起态（9 信用 / 8 储蓄） | 资产页 792pt | **0** |
| 浮层 · 信用 9 个 | 清单区 752pt 装 1120pt | 滚动（一屏 6.5 行） |
| 浮层 · 储蓄 8 个 | 清单区 752pt 装 1004pt | 滚动（一屏 6.5 行） |

对照：v4 平铺 5 个信用账户时信用组 587.5pt，收起态压到 279.2pt（**−52%**）；v5 再压到 101pt（**−83%**）。

### 覆盖层的规格（v6 浮层骨架 + v7 行规格）

| 项 | 值 | 为什么 |
|---|---|---|
| 容器 | `inset:0`，没有任何圆角/把手/上边距 | 圆角 + 把手是 sheet 的语法，一出现就被读成"弹出的半屏页" |
| 磨砂 | `rgba(247,245,241,.42)` + `backdrop-filter:blur(12px) saturate(1.16)` | 12px 是「色块可辨、文字不可读」的分界（22px 时底下的页面彻底消失，见 v6 实测） |
| 状态栏 | 在磨砂层**之上**重绘（9:41 + 电池），颜色与资产页一致 | 状态栏是"同一屏"的锚点；磨砂连它一起糊掉，就会读成新页面 |
| 关闭 | 右上 30pt ✕（`top:53 / right:16`）+ 点任意空白磨砂区 | 没有把手，必须留一个明确的退出位 |

| 行 | 高 116pt（`padding:10px 0`），卡面 144×96 圆角 15，右 gap 13，两列各 96.5 gap 8 | — |

### 还款进度怎么放（用户明确要求「负债卡底部有还款进度」）

两处，规格必须分开：

| 位置 | 规格 | 原因 |
|---|---|---|
| 收起态（132×82 卡堆前卡） | 卡内流式，离卡底 9pt，高 2.5pt，轨道 `rgba(255,255,255,.32)`，填充纯白 | **不能贴底**：贴底会和后层错位露出的 9pt 合并成一条，读成「两层」，堆叠感被吃掉 |
| 明细行（144×96 卡） | **内缩** `left/right:10pt`、`bottom:5pt`、高 3pt、圆角 2pt，轨道 `.30`、填充 `.95`；`.obot` 下内距加到 13pt 让位 | 贴底通栏会被卡的 15pt 圆角裁成一条月牙，读作「卡片缺了一块」；内缩后才读作「卡内进度条」 |

> 这条在 v6 一度被删（当时把"卡面多一条线"算进"杂乱"），v7 用户明确说「还款小白条设计挺满意」，恢复。**真正密集的是右侧三行文字，不是这条 3pt 的条。**

> 卡堆缩小到 132×82 后，前卡只剩「银行名 + 卡号 + 网络标 + 进度条」四样，`已还 67%` 这类文字放不下了——**收起态靠形态、详情页靠数字**，两级分工。

### 已知取舍

- **账户少于 3 个时堆叠偏薄**（只有 2 层后层）。账户少于 2 个时应退化为单卡（不露边），否则露 1 层会被读成投影。
- **进入账户要两步**（点卡堆 → 点账户）。这是卡牌堆的固有代价，用户已明确接受，换来的是「画面更干净」+「和首页呼应」。
- 收起态一屏只能看到每组当前的一张，横向比较必须点开浮层。
- **收起态与明细行都不显示「已还 N%」文字**，精确数字在详情页。
- **清单 8 行以上需要滚动**（752pt 装 1004~1120pt）。因为没有头部，滚到哪里都只有行本身，不丢上下文。
- **全屏磨砂的成本**：整屏 `backdrop-filter: blur(12px)` 是持续重绘，真机上必须用系统 `UIVisualEffectView`（或 `.ultraThinMaterial`），自绘模糊会掉帧。
- **「降低透明度」开启时 material 会退化成实色**：回退到 `Color(hex:0xF7F5F1).opacity(0.96)`，不能让文字压在彩色卡面上。

> 又一课：卡牌堆第一版错位只给 4pt，截图里完全看不出层次。**4pt 是「边」的量级，8pt 起才是「层」的量级**——和首页叠层 v2 的教训相同。这轮又补两条：**层数 ≥3 时仅靠错位不够，必须有显式的亮度阶梯**；**同一列里两张卡面的"装饰"必须对称，信息量不同可以用列表达，装饰不同会让整列读起来是乱的**。

### 后层材质：v4 试了 4 种，v5 又改一次

| 方案 | 结果 | 结论 |
|---|---|---|
| 后层用账户真彩色 | 三层是「红—蓝—红」，第三层与第一层同色系，读成"卡片带了一条彩色厚边" | 废弃 |
| 后层用纯白卡背 | 与页面底 `#F7F5F1` 只差 1.5%，**几乎隐形** | 废弃 |
| 后层白 + 该卡颜色 16%~32% 淡染 | 层次太弱，1.35 倍放大下才勉强数清 | 废弃 |
| 后层真彩色 + 底部 3pt 纯白"纸厚" + 越深越暗 | v4 满宽卡（104pt 高）成立，每层自带一条白线 | v4 采用 |
| **后层真彩色 + 纯亮度梯度（.87 / .74），不加白线** | v5 卡高只有 82pt，3pt 白线占 3.7%，读成"卡片描了白边"；改用投影天然分界 | **v5 采用** |

### v9 修正（2026-11-07：用户要求与首页卡堆对齐）

用户：「**将资产卡堆的效果和首页卡堆对齐**」。

上面那句「两套形态不该统一」被推翻。但推翻的方式**不是照搬首页参数**——直接抄过来会更糟，因为首页那套成立有前提：

| | 首页日卡 | 资产卡（v5） |
|---|---|---|
| 卡尺寸 | 358 × 722 | 132 × 82 |
| 圆角 | 24pt | 13pt |
| 层厚 | 10pt（占卡高 1.4%，露出的面积很大） | 9pt（**整条落在 13pt 圆角区内，被圆弧切掉**） |
| 旋转 1° 的角部外扩 | **12.6pt**（722 × sin1°） | **1.4pt**（82 × sin1°） |

两条从尺寸里推出来的规则：

1. **后层必须白纸**，不能用账户彩色。三层彩色小卡挤在 146pt 宽里必然糊成一块；而白纸的分界来自描边和台阶投影，与颜色无关。附带好处：`stack` 字段、`pickBacks`、`hueGap`、`lum` 整套挑色逻辑全部作废删除。
2. **层厚必须大于圆角半径**。9pt < 13pt → 露出的只是个月牙；**16pt > 13pt** → 露出「一段直边 + 圆弧」，层才数得清。这是 v1.0 的 9pt 失败的直接原因。

旋转的结论相反：**小卡不能靠旋转表达散叠**。旋转的视觉量与卡高成正比（12.6pt vs 1.4pt），硬要转 8° 才等价，但那就真成"被揉过"了。所以小卡的散叠感靠**下沉 + 左右交错**承载，旋转只保留 0.8°~1.0° 作为「手放上去」的暗示。

| 项 | 首页日卡 | 资产卡堆（v9） |
|---|---|---|
| 后层材质 | 白纸 + 1px 描边 + 窄投影 | **完全一致** |
| 层厚 | 10pt × 3 层 | 16pt × 2 层 |
| 左右交错 | 内缩 9~12pt | ±4pt（k1 右 / k2 左） |
| 旋转 | ±1.0~1.3° | ±0.8~1.0° |
| 前卡 | 白卡 | **彩色账户卡**（唯一保留的差异） |

> 教训：**对齐的是语言，不是数值**。同一个参数在 358 宽的卡上成立、在 132 宽的卡上失效，中间差的是「层厚 / 圆角」和「高度 × sinθ」两个比值。照抄数值只会得到一个更糟的版本。

struct AccountRow: View {

      }
      .frame(maxWidth: .infinity, alignment: .leading)
    }
    .frame(minHeight: 116)
  }

  // 每列只有两行：标签 + 数值
  private func col(_ label: String, _ value: String, _ tint: Color) -> some View {
    VStack(alignment: .leading, spacing: 6) {
      Text(label).font(.system(size: 10.5)).foregroundStyle(Color(hex: 0x9A968D))
      Text(value)
        .font(.system(size: 16.5, weight: .semibold))
        .foregroundStyle(tint)
        .monospacedDigit().lineLimit(1).minimumScaleFactor(0.85)
    }
    .frame(maxWidth: .infinity, alignment: .leading)
  }

要点：

- **不要用 `.sheet`**，哪怕加 `.presentationBackground(.ultraThinMaterial)` 也不行：detent（`.fraction(0.85)`）、顶部圆角、拖动把手、以及"内容从下方升起"的位移，四样加起来就是一句"这是半屏页"。用户要的是"同一屏被蒙住"。
- `.ultraThinMaterial` 必须放在 `.background`，且盖在 `Color.clear` 上，才能模糊**身后同一 ZStack 的兄弟视图**；如果把它放在不透明容器里，它只会模糊自己内部。
- 磨砂层的 `onTapGesture` 和列表要分层，否则点列表也会关闭。
- **`.sheet` 是行不通的但仍要记住的一点**：如果你非要保留系统 sheet 的交互（下滑关闭、手势转场），那视觉上就不可能做到"整屏朦胧"——这两件事在 iOS 上是互斥的。选视觉。
- 明细行的 `−3,120.00` 用 `.monospacedDigit()` + `lineLimit(1)` + `minimumScaleFactor(0.85)`，96.5pt 列宽下实测不换行。
- 卡堆的 `.brightness(-0.06)` 在深色卡（`#3C3C43`）上几乎无效，深色卡本来就读成黑，不需要再压暗——可加判断：底卡亮度 < 0.3 时跳过 brightness。

> **给实现者的硬要求**：这一步不是"原型凑合一下"。用户明确说过「如果原型做不到没关系，但是 app 内需要实现」。原型用 `backdrop-filter` 已经做到了；SwiftUI 必须用上面的 ZStack + material，**不接受降级成 sheet**。
