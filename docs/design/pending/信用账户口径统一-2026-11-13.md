# 信用账户口径统一

> 状态：**待定案**
> 日期：2026-11-13
> 范围：**仅信用账户**。储蓄 / 现金 / 借款三类账户已天然是「余额唯一真源」，本方案不动它们。
> 级别：**2.0 级**（AGENTS 6.2）——改核心口径，需用户确认后实施。

---

## 一、要解决什么

同一个「欠款」，现在有四个来源：

| 数字 | 位置 | 读什么 |
|---|---|---|
| 我欠（资产页标题） | `CardDebt` | 余额 + 账单 + 分期 |
| 我欠（走势 / 环比） | `NetWorth.owe` | `Σ(−余额)` |
| 欠款（详情页三列） | `CardDebt` | 同上 |
| 可用额度 | `limitBar` | `CardDebt` |

两个实测故障：

1. **记一笔 1.00 × 3 → 本期消费 +1,003，欠款一分不动。** 因为 `max(0, −余额)` 在余额 ≥ 0 时恒为 0，而 `createdFromEntry` 又把新建计划从分期项排除，那笔钱两处都不算。
2. **额度 100、存量分期欠 9,000、再记 1 元。** 只读余额的口径会答「欠 1.00」，实际欠 9,001.00。

两处故障同源：**债有两个账本（余额 / 账期），而它们从不核对。**

---

## 二、三类账户的位置

| | 储蓄 / 现金 | 信用 | 借款 |
|---|---|---|---|
| 余额含义 | 我的钱（正） | 欠的钱（负） | 欠的钱（负） |
| 什么会改它 | 流水 | 流水 + **分期入账** | 流水 |
| 额度 | 无 | 有，**只做分母** | 无 |
| 账单周期 | 无 | 有，**只答「本月要还」** | 无 |
| 分期计划 | 无 | 有，**只答「何时还完」** | 可选 |

统一后，**信用账户在「欠多少钱」上与借款账户完全一致**：`max(0, −余额)`。父母借款 20,000 从未出过问题，正是因为它只靠这一条。

---

## 三、统一规则（只有一条）

> **金额只由余额决定。额度做分母，账单做对账，分期做时间表。**

```
欠款 = max(0, −currentBalance)
```

余额里必须包含所有真实债务——包括分期计划里的那部分。所以分期计划**不能只登记**，必须入账一次。

---

## 四、五个动作

| 动作 | 余额 | 计划 | 欠款变化 |
|---|---|---|---|
| 记一笔消费（不勾分期） | −x | 不建 | +x |
| 记一笔消费（**勾了**分期） | −全额 | 建计划，**不再入账** | +全额 |
| 详情页录存量分期 | **−remainingDue** | 建计划，**入账** | +remainingDue |
| 还款一期 | +amount | 标记 `paidAt`、重算剩余 | −amount |
| 利息 / 违约金 / 年费 | −x（新入口，见第九节） | 无 | +x |

关键：**余额与期表只在「建计划」和「还一期」两个时刻变化，且每次变化量相同。** 它们不再是两本账，而是同一本账的两个视图——不同步就会立刻算术不自洽，不需要靠人工发现。

---

## 五、`createdFromEntry` 语义反转

| | 现在 | 统一后 |
|---|---|---|
| 含义 | 「排除我，不要算我」 | 「**我已入过账，不要再入一次**」 |
| 用在 | `CardDebt` 跳过它的未还期 | `InstallmentService` 建计划时不重复入账 |

字段保留，语义更准。它正好是「同一笔债不能有第二个金额来源」这条规则的实现。

---

## 六、两个边界（2026-11-13 已定向）

### 边界 1：改计划时余额的联动 —— 按推荐方案

**只有「剩余应还」有资格改余额。**

| 改动 | 余额 | 期表 |
|---|---|---|
| 改 `remainingDue` | **同步差额** | 连带重摊 |
| 改期数 | **不动** | 重摊 |
| 改单期金额 | 不动（见下） | 重摊其余期 |

理由：期数回答的是「分几期还」，不是「欠多少」。把「12 期改 10 期」当成欠款变化，会让「我还剩多少钱」和「我分几期还完」这两件事一起漂。

改单期金额这一条要收紧：单期金额由系统摊平，**不允许手改**。真有单期差异（银行多收 5 元），走「剩余应还 +5」再重摊，这样差额只有一个出口。

> 这条会影响 `docs/design/spec/账户详情页规格冻结-v1.0.md` 第十一节未锁定项「分期逐期改」的字段范围，实施时按 1.x 补一行修订记录。

### 边界 2：同一笔债录两次计划 —— **不做任何处理**（用户决定）

两次录入数据完全相同（金额、期数、日期都可能重复），App 无法判断是「同一笔」还是「真的又买了一次」。不做自动去重、不做重复检测、不弹提示。

记为**已知限制**，写进本文件即可，不写代码。

危害与自愈路径：
- 余额会多算一次 → 欠款偏高
- 但「本月要还」会多出一期，异常立刻显形，能自己发现
- 旧口径下此错误同样存在（且方向更糟：两边都加），故不是本方案引入的

## 七、迁移（每张信用账户一次）

### 步骤

1. 详情页显示两个数：**当前欠款**（`max(0,−余额)`）、**分期未还合计**（Σ `remainingDue`）
2. 提供两个出口：
   - **「按银行 App 校准」**：输入信用卡 App 上的当前欠款，一次性校准
   - **「把分期合计计入欠款」**：差额 = 分期合计 − 当前欠款，一次性补入
3. 校准后写回 `initialBalance`，`recalculateAll` 复核

### 花呗的具体数（本次已知）

| 项 | 值 | 说明 |
|---|---|---|
| 截图欠款 | 2,852.15 | `max(0,−余额)` = 0 → **余额 ≥ 0** |
| 分期未还合计 | 3,852.15 | 含 11-13 当天新建的 1,000 |
| 真实欠款 | **3,852.15**（待用户按支付宝核对） | 少算的 1,000 即 `createdFromEntry` 排除的那笔 |

迁移后：余额校准至 −3,852.15，欠款 3,852.15，那笔 1,000 自动回来。

### 已知副作用

- `initialBalance` 会变成**校准旋钮**，失去「建账那一刻的余额」的语义。可接受的替代是记一条 `adjustment` 流水（见第九节未决项 1）。
- 存量「花呗分期存量」账户（−4,000）与「花呗」下的 8 笔计划（3,852.15）疑似同一批债。统一后**金额不受影响**（计划不再计金额），但两个容器的「本月要还」可能重复，迁移时建议核对后合并。

## 九、已定项（2026-11-13 用户定向）

| 项 | 结论 |
|---|---|
| **分期含息** | 录入时按待还总额填（含息），欠款即含息总额。PRD 9.3 不变，**不需要任何额外入口** |
| **额度超限** | 进度条封顶 100%，不显示负数可用额度 |
| **同一笔债录两次** | 不处理（边界 2） |
| **账单区块** | 即详情页「往期账单」（`BillEntrySheet`），**文案不改**；身份是「本月要还的金额来源 + 对账凭证」 |
| **迁移** | **不弹窗**。当前真机数据是演示数据，不值得为它做核对流程 |

### 利息与违约金：只做提醒，不做识别

**不做**：App 不去判断哪家银行、哪种产品、按什么费率计算。各银行的循环利息、违约金、年费规则差异大且随时调整，硬算等于编造，反而摧毁信任。

**做**：信用账户**出现逾期时**提示一句「本期可能已产生利息或违约金，请到银行 App 核对后填入」。

- 用户填两个数（利息、违约金），App **只记录，不推算**
- 两个数同时产生两个效果：

| 效果 | 说明 |
|---|---|
| ① 计入**本期应还** | 「本月要还」随之变大 |
| ② 计入**欠款** | 余额 −x，`max(0,−余额)` 随之变大 |

第 ② 条不能省。若只加本期不加余额，用户按账单还完之后余额会变成 **+x**，界面显示「溢缴 x」，即 11-13 那个 bug 换壳重现（消费 1,000、利息 25.17、还 1,025.17 → 余额 +25.17）。

- 记账属性：**不计入消费统计**（PRD 9.3「利息不算支出」）
- 实现待定：走 `expense` + 「不计入统计」标记，还是新增一个轻量类型

## 十、未决项

1. **利息/违约金的记账形态**：`expense` + 不计入统计标记 vs 新增轻量类型。
2. **已有计划的一次性入账**：切换口径时，库里已存在的 `Installment`（真机 8 笔、合计 3,852.15）必须**静默把 `remainingDue` 计入余额**，否则这批计划永远不进金额，成为僵尸数据。这是数据迁移，不是弹窗确认，无界面交互。

---

## 十一、本轮不做

- 不改任何生产代码（AGENTS 6.2：2.0 级变更需先确认）
- 不动 `DueMath` / `DetailMath` 的口径
- 不做利息入口（未决项 1）
- 不做「同一笔债录两次」的检测（边界 2 已决定不处理）
