**现金**：v1 **暴露**（2026-11-13 定案，推翻此前「不单独管理」）。`.cash` 与储蓄同构——余额正 = 我的钱、无账期、无分期、无额度、不出现在「本月要还」里。理由：手里的纸币进出如果完全不计，净资产会长期偏离真实值；四类账户都由用户自由增删，成本只是多一个选项。

### 3.1.1 账户分类原则（v1.3 调整）

不再使用「资产 / 负债」的会计二分，改为按**使用方式**四分：

| 分类 | 含义 | 判断标准 |
|---|---|---|
| 储蓄 | 钱在我这，可随时转出 | 银行卡、余额宝、小金库、微信余额 |
| 现金 | 手里的纸币 | 钱包 |
| 信用 | 我欠机构的 | 信用卡、花呗、白条、月付、分期、贷款 |
| 借款 | 我欠个人的 | 亲友借款 |

**这样分的原因**：用户不需要做会计判断（「花呗算资产还是负债」）。而且两个核心问题直接对应两个加总：

```
我有多少钱 = Σ储蓄 + Σ现金
我欠多少钱 = Σ信用 + Σ借款
净资产     = 前者 − 后者
```

**账户数量不固定**，全部由用户自行增删，产品不预设清单。

**两处边界（2026-11-11 定）**：

- **水费 / 电费**：「水费」只记水，「电费」记电与燃气，两格语义不重叠——拆开的目的是让水的钱单独看得见。

### 3.3 三条从数据里读出来的结论

**结论一：分期是常态，不是例外。**
58 笔在读分期意味着产品必须同时具备两条**互不替代**的路径（v1.8 修正，原文把两者混为一谈）：

| 路径 | 处理对象 | 解决什么 | 录入成本 |
|---|---|---|---|
| **A 存量录入** | 已发生的 58 笔 | 让历史分期能被汇总进「本月要还」和结清预测 | 每笔约 5 个字段，58 笔 = 58 次轻量操作 |
| **B 记一笔时创建** | 以后每一笔分期消费 | 不用「先记消费、再另开界面建计划」走两遍 | 记账时多勾一下 |

**B 不能替代 A**：58 笔已经发生了，没有「付款那一刻」可以拦截。**A 也不能替代 B**：靠 A 的办法处理未来每一笔，等于每天多开一次界面。

A 的成本靠「不录历史明细」压下来（见 9.5.4），B 的成本靠「记一笔内联开关」压下来（见 9.5.6）。

**结论二：还款额波动极大。**
京东白条月还款：997.57（1–6 月）→ 909.37（7 月）→ 2,323.44（8 月）→ 1,569.64（9 月）→ 613.16（10 月）。任何「固定月供」的假设都会算错。

**结论三：逾期已经发生过。**
招行 2026-08 账单逾期，产生违约金与循环利息，额度被下调一半。产品必须有逾期预警，且预警要提前，不是事后显示。

## 四、一天里的四个时刻

**时刻一 · 刚付完钱（每天 3-5 次）** → 别让我在这儿多待
**时刻二 · 发薪日（每月 1 次）** → 这个月还完债能剩多少
**时刻三 · 还款日前 / 月底（每月 3-5 次）** → 哪几张卡几号还、够不够
**时刻四 · 想知道我有多少钱（不定时）** → 进资产页看

## 五、八条核心决策（已定稿）

| # | 决策 | 结论 | 落地要求 |
|---|---|---|---|
| 1 | 信用卡还款怎么记 | **不计入支出** | 还款 = 负债减少 + 资产减少，属转账。必须与消费统计完全隔离 |
| 2 | AA / 我先付的场景 | **只记我承担的部分** | 垫付部分单独成为一个功能，不能靠「一次支出 + 一次收入」模拟 |
| 3 | 账户互转（微信提现） | **账户互转，不计收支** | 但**手续费要单独记为支出**（用户批注：微信提现是有手续费的） |
| 4 | 退款 | **冲减原分类支出** | 不做收入，避免虚增当月收入 |
| 5 | 统计口径 | **自然月**（1 号到月底） | 账单周期只用于负债，不影响消费统计 |
| 6 | 循环负债怎么录 | **每月手录本期应还** | 不推演。平台给的数字才是准的 |
| 7 | 分期怎么录 | **填剩余期数 + 每期金额 + 首期还款日**（3 个必填） | 不填年化利率，由 App 反算（见 9.5.2） |
| 8 | 亲友借款 | **当借款账户处理，不进还款体系** | 只记总额 / 已还 / 剩余；无月供、无还款日、无逾期（见 9.10） |

### 5.1 你在决策表里提的六个追问，逐条回答

**问：「不计入支出的话，还款这个动作是什么意思」**

还款不是「花钱」，是「把欠的钱还上」。它同时改变两个东西：负债账户欠款减少、资产账户余额减少。你的**总支出不变，净资产不变**，只是负债结构变了。

算成支出会这样出错：10 月刷卡吃饭 300（记支出 300），11 月还信用卡 300（又记支出 300），那个月你「花了 600」，但只吃了一顿饭。

所以产品里需要独立的操作类型 `还款`，产生两条账务影响，但**不进任何消费统计**。

**问：「微信提现有手续费」**

转账可以带手续费。转出 1,000、手续费 1，记一条转账（1,000）加一条支出（1 元，分类「手续费」）。手续费是真花掉的钱，必须计入。

**问：「亲友是不是也可以理解成一个账户」**

是。亲友借款就是负债账户的一种，只是没有利率、没有账单日。统一进账户模型，不单开类型。

**问：「花呗支付时，怎么知道算哪一期」**

花呗账户要有账单周期字段（你的周期 10/15–11/14，还款日 25 日）。选花呗付款时按当天日期自动判断：
- 落在 10/15–11/14 → 计入 11 月账单（11/25 还）
- 落在 11/15–12/14 → 计入 12 月账单（12/25 还）

界面要让用户看得见「这笔将进入 12 月账单」，可手动改。

**问：「AA 那笔能不能单独摘出来」**

可以，但要控制成本。v1 做法：记支出时勾选「有垫付」，填对方应还金额，差额存成「待收」条目，收回时冲平，不计收支。v1 不做完整应收款管理。

**问：「自然月和发薪月有什么区别」**

- **自然月**：11/1–11/30。所有账单、报表按这个算，和你看到的所有平台账单对得上。
- **发薪月**：10/15 发薪到 11/15 发薪。能看出「一个工资周期花了多少」。

你选了自然月，理由是**和平台账单对得上**。代价是「这个月工资剩多少」要单独算。这个代价可以接受。

## 八、数据模型

**分层约定（v1.8 明确）**：账户只是容器，只装「名字 / 类型 / 额度 / 账单周期 / 还款日 / 当前欠款」。
**期数、每期金额、利率一律不属于账户，而是属于挂在账户下的 `DebtPlan`**。

因此一个信用账户可以是：

| 形态 | DebtPlan 数量 | 例子 |

| 纯循环 | 0 个 | 花呗、白条、抖音月付、信用卡本体 |
| 纯分期 | 1 个或多个 | e招贷、消费分期-中移金科 |
| 混合 | 1 个循环 + N 个分期（共用额度） | 招行信用卡 8857（本体 + 3 笔分期） |

**创建账户时不问期数，也不问利率。** 利率（`impliedAnnualRate`）只是反算出来的只读展示值，任何录入界面都不出现。

## 九、关键规则

### 9.1 消费统计口径

**只有 `expense` 计入消费。** `repayment`、`transfer`、`adjustment` 一律不计入。

支付宝账单里「账户存取」7,098 元就是被误算的典型——那是提现和转账，不是消费。

### 9.2 资产账户余额

```
余额 = 期初余额 + Σ收入 − Σ支出 − Σ还贷 − Σ转出 + Σ转入
```

### 9.3 负债账户欠款

```
欠款 = 期初欠款 + Σ消费(该账户付款) + Σ利息 + Σ违约金 − Σ还款
```

**口径补录（2026-11-12，e招贷 定案）：分期/贷款的「期初欠款」填含息的待还总额，上式里的 `+ Σ利息` 就不再逐期累加。**

- 账单给「本金 6,670.93 + 利息 851.57」时，账户欠款填 **7,522.50**（= 442.50 × 17），不是本金那一行。
- 之后每期还款 **442.50 全额冲减**，第 17 期正好归零。若按本金记，24 期走完会显示欠款 **−1,620**——那多出来的一笔是利息，它花掉了但没还掉任何债。
- 逐期本金/利息**不入库**（`InstallmentPeriod.principal` / `interest` 保持 `nil`），利息也**不算作支出**：用户只关心「这个月要还多少、还剩多少」，不关心 442.50 里各占多少。
- 代价：净资产从第一天起就少算未来利息（本例 851.57）。这是保守口径，也是房贷计算器的口径——它的概览卡主数字就是「还款总额 = 本金 + 利息」。
- 「剩余本金」只服务**提前还款**（提前还的是本金、未来利息作废）。v1 不做提前还款，因此这个字段与逐期拆分整条不建。
- **拆两栏时年化走剩余口径**：`现值 = 剩余应还 − 剩余利息 = 剩余本金`（e招贷 6,670.93），配**剩余期数** 17，反算 16.43%。这类利息存 `Installment.remainingInterest`，**不进 `totalInterest`**——后者是整笔语义，拿剩余利息套整笔公式（24 期）会把 16.43% 报成 8.2%。一期没还时剩余 = 整笔，两个口径同解，所以新贷录入不受影响。

### 9.4 净资产

```
我有多少钱 = Σ储蓄账户余额 + Σ现金
我欠多少钱 = Σ信用账户欠款 + Σ借款账户欠款
净资产     = 我有多少钱 − 我欠多少钱
```

**口径补录（2026-11-13 定案，推翻 11-12 的「余额与账期相加」）：单卡欠款 = `max(0, −currentBalance)`，多卡逐卡取正再求和。**

```
单卡欠款 = max(0, −currentBalance)
我欠     = Σ 各负债卡 max(0, −currentBalance)
```

- **额度、账单、分期都不产生金额**：额度只作分母（可用额度 = 额度 − 欠款）；账单只答「本月要还」；分期只答「何时还完」与「本月到期多少」。判据：如果还需要一个 `CardDebt` 来推导欠款，就说明没统一。
- **为什么推翻 11-12 的派生口径**：旧口径把同一笔债拆在「余额」和「账期」两个从不核对的账本上——余额被还款流水推成正数时 `max(0,·)` 把它丢掉，`createdFromEntry` 又把记一笔建的计划从账期项排除，于是那笔钱两处都不算（真机表现：记一笔 1,000 元分期，「我欠」一动不动，连不勾分期的 1.00 也不动）；反过来，同一笔债既有流水又有分期时又算两遍（1,440.39 变 2,880.78）。同一处代码在不同余额下既会多算也会少算，不是稳定口径。
- **分期建计划必须入账一次**：`InstallmentService.insert` 在 `createdFromEntry == false` 时把 `remainingDue` 计入余额；记一笔里建的计划（`true`）由那条全额消费入账，不再重复。只登记不入账会让期表里的债在「我欠」里彻底消失。
- **只统一信用账户**：储蓄 / 现金 / 借款本来就已经是「余额唯一真源」——父母借款 20,000 从未出过错，因为它只靠一个数。
- **「我欠」只允许有一份数据**：聚合层只产出「账户 → 逐卡**已取正**欠额」这一份字典，合计由 `CreditDebt.total(ofOwed:)` 现算，视图不得另存 `@State owe`。真机出现过顶部「我欠 0.00」与信用组头「-22,772.69」同屏。
- **`CreditDebt` 两个入口别混**：`owe(balances:)` 收**余额**（内部 `max(0, −x)`）；`total(ofOwed:)` 收**已取正欠额**（只相加）。
- **与「本月要还」不是一回事**：「本月要还」是**单一账期**的到期额，账单与本月到期分期二选一（9.12）；「我欠」是**所有未还债**的总额，只由余额派生。别把两条口径混成一条。
- 口径实现：`Math/CreditDebt.swift`，断言在 `DooDooTests/CreditDebtTests.swift`。

### 9.5 分期展开

**总原则三条：**

1. **历史照账单填，未来由 App 算**
2. **只填能看到的，看不到的由 App 反算**
3. **金额优先，利率是结果不是输入**

#### 9.5.1 为什么不能要求填年化利率

年化利率是银行内部的定价参数，**付款页和账单里都不显示**。

用户实际能看到的信息只有这些：

| 场景 | 平台显示 |
|---|---|
| 京东付款页 | ¥1278.07 × 12 期｜减 131.85 元｜含利息 ¥89.16/期 |
| 花呗账单 | 分期总额 1440.39｜含利息 110.56｜每期 120.03（含利息 9.22）｜贴息减免 0.53 |
| 招行账单 | 分期还款 本金 第6/12期 82.67｜分期利息 6.55 |

**所有界面都不给年化利率。** 把它设为必填，等于要求用户填一个拿不到的数字。

#### 9.5.2 录入字段（改后）

| 字段 | 必填 | 说明 |
|---|---|---|
| 剩余期数 | 是 | 还能还几次 |
| 每期金额 | 是 | 等额时填这个，如 120.03 |
| 首期金额 | 否 | 首期不同时填，如 120.06 |
| 末期金额 | 否 | 末期不同时填（如余数、优惠落在末期） |
| 剩余本金 | 否 | 有的话填，用于更准地反算 |
| 总利息 | 否 | 账单上的「含利息」，如 110.56 |
| 首期还款日 | 是 | |

**没有「年化利率」这一栏。** 它是输出，不是输入。

#### 9.5.3 App 反算年化（新增能力）

用户填完上面几个数，App 用现金流反算真实年化，展示在详情页：

```
每期 120.03 × 12 期，含利息 110.56
真实年化 ≈ 15%
```

算法：以「本金 = 每期金额 × 期数 − 总利息」为现值，每期金额为年金，求解月利率后 × 12。

**这个数字是所有平台都不显示、但对用户最有用的数字。** 它是这个 App 相对于账单页的增量价值。

标注「估算」，不参与任何账务计算。

#### 9.5.4 历史与未来的分工

| 时间段 | 数据来源 | 存储粒度 |
|---|---|---|
| 已发生（已还期数） | 用户照账单填 | **只存汇总值** |
| 未来（未到期数） | App 生成 | 逐期存 |

理由：

- 过去每期金额只有账单知道（含利息、贴息、退款抵扣、余数分配），App 算不出也不该猜
- 58 笔分期逐期录历史，成本高到不可能坚持
- 未来没有账单可抄，适合推算
- 历史明细不丢——那笔消费已在流水里

#### 9.5.5 未来期数的生成

已知「每期金额 + 期数」时，直接平铺，不做利率推演：

- 期数 × 每期间隔（默认每月，取首期还款日的日号）
- 若填了首期/末期金额，中间期数按等差插值
- 生成后任意一期都可手工改，标记 `isManualOverride`

**余数处理**：默认放末期，可切换放首期。

例：6,699 ÷ 24 = 279.125，平台给每期 279.13，24 期合计 6,699.12，多 0.12。
这 0.12 在招行摊进末期还是首期，只有账单知道——生成值只是草稿，最终以账单为准。

### 9.5.6 记一笔时创建分期（v1.8 新增）

**场景**：在京东付款页选了 12 期，或在花呗选择分期付款。此刻钱没有从储蓄卡扣走，而是变成对平台的欠款。

**做法：不是新开一个「建计划」界面，而是为「记一笔」加一个开关。**

```
记一笔 → 类型=支出 → 账户=花呗 → 金额=1440.39
                                    ☑ 分期  期数 12  每期 120.03
                                    首期 2026-12-10
```

提交后一次性产生两样东西：

1. 一条 `Transaction`（kind=.expense，金额 = 分期总额，账户 = 花呗）
2. 一个 `DebtPlan`（remainingPeriods=12，periodAmount=120.03，firstDueDate，`originTransaction` 指回第 1 条）+ 12 条 `Installment`

**为什么消费必须记全额，不能只记每月分摊额**

PRD 9.3 的欠款公式是 `欠款 = 期初欠款 + Σ消费(该账户付款) + Σ利息 − Σ还款`。如果这笔只记 120.03，花呗欠款会少算 1,320.36，与真实账单对不上。全额入账后公式才闭合。

代价是消费统计把利息也算进去了（这笔含利息 110.56，约占总额 7.7%）。月均流水约 7,500 元时误差在 1.5% 量级，且 v1 不做统计图表，因此接受。

**与存量录入的区别**：9.5.2 那套字段是给「已存在的分期」用的（要填剩余期数）；这里是新发生的，期数就是全期，首期日就是下一个账单日。

> **实现补录（2026-11-13，M3-10 落地，口径不变）**
>
> | 项 | 落法 |
> |---|---|
> | 开关位置 | 记一笔 → 支出 → 付款账户是**信用/借款**时，金额下方出现「分期」开关；储蓄/现金不出现（当场扣钱，没有「以后还」这回事） |
> | 要填的 | 期数（3 / 6 / 12 / 24 四档 chip）+ 每期金额（**留空自动 = 总额 ÷ 期数**）+ 首期还款日（默认按账户 `dueDay` 推下一个还款日） |
> | 提交结果 | ① 一条全额 `expense`；② 一张 `Installment`（`totalPeriods` = 期数、`paidPeriods = 0`、`remainingDue` = 全额、`createdFromEntry = true`）+ 展开的未来逐期 |
> | 差额处理 | 每期 × 期数与总额**差 ≤ 1 元**照收（除不尽，余数落首期，与 9.5.2 同一套 `splitEvenly`）；差超过 1 元**拦下**，不静默摊出一张对不上的表 |
> | 「我欠」 | 这种计划**不进账期那一项**——消费全额已在 `currentBalance` 里，再加一次就是双份（1,440.39 的平板会显示成 2,880.78）。判据是 `createdFromEntry`，不是「余额有没有变」 |
> | 仍会重复的一种 | 同一笔既有流水、又手工录了账单时有重复（见 9.3 已接受的代价）；逐月录账单启用后按 9.12 对账，届时再处理 |
>
> 「分期总额」这个数**只在界面展示**，不单独落字段：它就是那条流水的 `amount`。

### 9.6 逾期

```
逾期 = 存在 Installment（或循环账单）的 dueDate < 今天 且 isPaid == false
```

| 状态 | 表现 |
|---|---|
| 逾期 | 信用组明细行末尾红字「逾期 N 笔 M 天」+ 浮层内该卡的「较上月」换成「逾期 M 天」；该笔金额**不计入**本月要还（属上一个账期） |
| 3 天内到期 | 黄色标记 |
| 未到期 | 正常显示 |

**不做横幅，也不做系统通知**（系统通知 v1.8 定，横幅 2026-11-12 定）。理由：系统通知需要权限、会被折叠、会打扰，而真正会逾期的人往往正是因为通知太多而忽略它；横幅则要么在信用组组头上方占掉一整条、要么把「我有 / 我欠」总览卡挤下首屏，而逾期只发生在信用卡上，挂在页顶会把「某张卡逾期」读成「整个账本出事了」。改成在信用组自己的明细行上标红——位置就在语义正中间，且**不新增任何结构**：`资产页规格冻结-v1.0.md` 2.4 那一行本来就是 `本月要还 2,742.00 · 3 笔 · 最近 11/08`。

**逾期不是统计功能，是一等功能。** 你已经为此付过 16.05 元违约金和一半的额度。

### 9.7 记一笔默认值

类型=支出，日期=今天，账户=上次使用，分类=上次使用，评分=该分类上次的档位，金额空并聚焦。

**日期归属（v2.1 补充）**：日期默认今天，但**用户可以改**，改到哪天这笔就归属哪天。

- 归属看的是 `Transaction.date`，不是 `createdAt`。`createdAt` 只用于排序和排查，永远不可改。
- 补记昨天的一笔时，保存后必须**保持当前浏览位置不动**，不能因为列表重排把页面弹回顶部——用户会以为没保存成功。
- 跨月补记（比如 11 月 1 日记 10 月 31 日的账）：那笔计入 10 月，当月统计随之变化，需要给一句提示，否则用户会以为统计出错。

**账单期归属（`Transaction.billPeriod`，2026-11-13 落地）**

「这笔消费算进哪一期账单」原本只有还款流水在写，现在记账时也写。规则只有三条：

| 项 | 规则 |
|---|---|
| 账期名 | **周期止所在月**：花呗 10/15–11/14 这一期叫 `2026-11`，11/25 还（与 `BillStatement.period` 同一口径） |
| 默认归属 | 按账户的 `billCycleStart` / `billCycleEnd` 与发生日算：没过账单日算本期，过了算下一期。11/14 仍属 `2026-11`，11/15 起属 `2026-12` |
| 手动调整 | 归属行那枚胶囊可切「本期 / 下一期」（商户延迟入账、跨账单日补记）。手动改过标「手动」，免得被当成自动值 |

- 储蓄 / 现金账户**没有账期**，`billPeriod` 保持 `nil`。
- 还款流水写**发生月**（11/25 还的记 `2026-11`），沿用账户详情页卡片级还款的口径。
- 这一项现在只做记录：将来「本期消费 vs 账单金额」对账（9.12）要用它，统计口径暂不受影响。

### 9.8 转账与手续费

真实场景：微信提现 1,000 元，银行卡实际到账 999.9 元，手续费 0.1 元。

**不能**用「转 1,000 + 另记一笔 0.1 支出」来实现——转账按 1,000 扣、再扣 0.1，转出账户会比实际多扣 0.1，余额对不上。

正确做法是**转账等额、手续费独立成一条**：

```
转账本金     转出账户 −999.9     转入账户 +999.9     ← 两边永远等额
手续费       转出账户 −0.1       （独立 expense，分类「其他 › 手续费」）
──────────
转出账户合计  −1,000             ← 与用户输入一致
净资产        −0.1
```

> **v2.3 补录（2026-11-10）**：本节原文写的是「转出 −1000 / 转入 +999.9 / 手续费 0.1 自动生成一条支出」，这三行自相矛盾——`1000 − 999.9` 本身就已经是 0.1 的净资产损失，再记一条 0.1 的支出会变成 −0.2。
> 早期实现按「转账扣全额、手续费只存 `fee` 字段不落流水」绕开了矛盾，代价是首页日卡看不到那条手续费：头部合计含手续费，列表里却只有 −1,000 的转账，两边永远差一截（真机反馈 #13）。
> 现改为等额模型，两个问题一起解决。

实现规则：

```
fee        = amount − receivedAmount
转账本金额 = receivedAmount
```

- `receivedAmount` 为空时，视为无手续费，到账 = 转出，**不生成**手续费流水
- 手续费 > 0 时，自动生成一条 `expense`（分类 `misc.fee`），与转账共用 `groupID`；删转账时按 `groupID` 一并软删，不留孤儿流水
- 转账行的**金额列显示到账额**（`amount − fee`），副标题写「转出 ¥amount」，两条流水相加正好等于用户填的转出总额
- 界面上输入「提现 1,000」，另一个小输入框填「到账 999.9」，或直接填「手续费 0.1」

### 9.9 退款

**普通支出退款**：冲减原支出，不改历史，不做收入。

**分期退款（依花呗真实机制）：**

v1.4 原写「作废剩余期数」，**这个是错的**。真实账单（2026-11-04 截图）显示：

> 1/6 期 已结清 33.20｜退款 33.20 元抵扣账单｜利息共减免 1.56
> 2/6 期 已结清 33.16｜退款 33.16 元抵扣账单
> ……
> 6/6 期 进行中 80.66（原 83.19）｜退款 60.00 元抵扣账单

**退款不取消期数，而是逐期「抵扣账单 + 标记已结清」，利息同步减免。**

两者账务含义完全不同：
- 作废 = 这笔钱当没发生
- 抵扣结清 = 钱确实走过一遍，又被退回来抵掉

**实现规则：**

1. 全额退款 → 每一期 `refundApplied = 该期原金额`，`status = .paid`，`dueAmount = 0`
2. 部分退款 → 按平台实际情况分配抵扣（花呗是抵到最后一期），逐期填 `refundApplied`
3. 利息随退款减免 → 填 `subsidy` 或直接下调 `interest`
4. 退款可退到未来账单（截图中「已退至 2027 年 2 月账单」）→ 允许 `refundApplied` 挂到任意未来期

**不做自动推算**：退款抵到哪一期、抵多少，由用户照账单填。App 只负责让每一期能单独设这三个数。

### 9.9.1 利息构成（v1.5 新增）

花呗分期**含利息**，不可假设免息。真实数据：

| 期数 | 应还 | 含利息 |
|---|---|---|
| 1/6 | 83.23 | 3.38 |
| 2/6 | 83.19 | 3.36 |
| 3/6 | 83.19 | 3.36 |
| 6/6 | 80.66 | 0.83 |

另有**国家贴息**（消费贷贴息政策），每期减免约 0.23，整笔可累计「已享利息减免 0.57」这类数字。

因此分期模型必须能拆出三层：**本金 / 利息 / 减免**，不能只有一个「每期金额」。

### 9.10 借款账户的例外规则

`kind == .loan` 的账户（亲友借款）与信用账户有本质区别：

| 能力 | 信用账户 | 借款账户 |
|---|---|---|
| 每月要还金额 | 有 | **无** |
| 还款日 / 逾期判断 | 有 | **无** |
| 期数 / 利率 / 分期 | 有 | **无** |
| 计入「本月要还」 | 是 | **否** |
| 计入结清时间预测 | 是 | **否** |

借款账户只维护三个数：初始欠款、累计已还、当前剩余。

还钱时记一条 `repayment`，扣储蓄、减欠款，不产生任何账单周期或逾期逻辑。

产品不催亲友借款，也不预测它什么时候还完——这是人情，不是债权。

### 9.11 余额策略（v2.0 新增，架构级决策）

**账户余额是派生值，不是真相。真相是流水。**

采用混合方案：

| 做法 | 为什么 |
|---|---|
| `Account.currentBalance` **存字段** | 读得快。纯实时算的话，10 万笔时每次打开账户页要扫全表，冷启动会超 1.5 秒 |
| 所有流水增删改**统一走 `LedgerService`** | 变更后立即重算受影响账户余额并写回。散落在各处的直接赋值必然漏更新 |
| 提供 `recalculateAll()` | 全量重算，用于数据修复、导入后校验、以及单元测试 |
| 流水**软删除**（`deletedAt`） | 硬删会导致历史不可回溯，余额出错时无法查因 |

**任何视图都不得直接修改 `currentBalance`。** 它只能由 `LedgerService` 写入。

### 9.12 汇总口径：本月要还

「本月要还」这个数字有两处容易算错，必须定死。

**第一条：每张卡只产出一个 `dueAmount`，账单优先，绝不相加。**

```
每张卡：本期账单 dueAmount > 0  → 取账单
        没有账单                → 取该卡本月到期分期之和
整组：  本月要还 = Σ 各卡 dueAmount
```

**不要**写成「Σ 本月到期的 Installment + Σ 本月到期的 BillStatement」。那条式子是错的：分期每期的钱本来就并进当期账单，两边各加一次会把分期算两遍。

```
错误：Σ账单 2,742.00 + Σ分期 693.67 = 3,435.67   ← 多出来的正好是三张卡的分期部分
正确：Σ各卡 dueAmount               = 2,742.00
```

代码里把「相加」这条路堵死：`DueMath.accountDue` 返回的是**单值**，不是两个数的容器，调用方拿不到「账单 + 分期」这种东西可加（`Math/DueMath.swift`，断言在 `DooDooTests/DueMathTests.swift`）。同一口径已在 `账户详情页规格冻结-v1.0.md` 第八节落地，两处必须一致。

**第二条：逾期不计入金额，但必须报出来。**

逾期那笔属于**上一个**账期（8 月该还的钱是 8 月的账单）。并进本月金额会让「本月要还」出现两个数——资产页 1,627.83、账户详情页 1,115.03，同词不同数。所以金额窗口只取本月：

```
计入金额的条目 = 未还 且 本月 1 号 ≤ dueDate < 下月 1 号
```

但不做横幅（2026-11-12 定）之后，逾期在资产页上没有第二个地方能看见。因此**逾期与金额分开统计**：笔数与天数跨窗口全量算，由信用组明细行末尾那段红字报出（` · 逾期 1 笔 82 天`），**不参与金额**。

本月内已经过了还款日的那一笔会同时进金额和逾期计数——它既属于本月账期、又已经过期，两者不矛盾。有逾期但本月无应还时，明细行写「本月没有应还」+ 红字，而不是把整行藏起来。

**第三条：账单从哪来（2026-11-12 接入）。**

上面那个「本期账单」来自 `BillStatement`，每月手录一次：账期（`2026-11`）、本期应还、还款日三个数。入口在**账户详情页的「往期账单」区块右上角「＋ 录账单」**（M3-8 起），同卡同账期重复录视为修订而不是新建。

- 有本期账单的卡：金额直接读 `dueAmount`，**该卡的分期一根手指都不碰**——账单里的分期部分本来就已经算在应还额里。
- 没录账单的卡：退回「本月到期的分期」。
- 往期逾期账单：不进金额，只进逾期计数（见第二条）。

**两条排除规则：**

1. **借款账户（`.loan`）一律不计入**（见 9.10）。
2. **已还的不计入**。

**「还完剩多少」的口径：**

```
本月可支配 = 月收入 − 本月要还 − 本月已花（不含还款与转账）
```

### 9.13 消费评分（v2.1 新增）

**每一笔支出都可以打分，四档，可跳过。评分不是消费的分类，是消费的"值不值"。**

| 档位 | 定义 | 例子 |
|---|---|---|
| 夯 | 主动花，花得值 | 一顿很爽的火锅、等了半年的耳机 |
| 飘 | 可花可不花，花了也没感觉 | 顺手买的奶茶、凑单的袜子 |
| 拉 | 花了就后悔 | 冲动下单、被推销的会员 |
| NPC | 不得不花，没有情绪 | 房租、话费、通勤、水电 |

**NPC 不是"最差"，是"无情绪"。** 这条是四档能成立的前提——如果把 NPC 当成最低分，它就和"拉"重复了，四档会退化成实质三档。

**四条实现规则：**

1. **默认值是 `nil`，不是 `.npc`。** 界面上可以让未评分的项显示成 NPC 的样式（灰、可点），但数据里必须区分。否则「用户判定它是 NPC」和「用户忘了打分」永远分不开，以后做不了「你这个月还有 60 笔没评」这类提醒，夯拉比例也会被"忘打分"污染。
2. **只有 `kind == .expense` 能有评分。** 收入、还款、转账、调整一律 `nil`。
3. **按分类记住上次档位。** 选"房租"自动带出 NPC，90% 的笔是零点击。这个记忆存在 `Category` 上（`defaultGrade: SpendGrade?`），用户改一次就更新。
4. **事后可补。** 流水条目支持补打分和改分。不补的话，用户在赶时间时永远不会打分，数据永远不完整。

**统计口径：**

```
夯拉比例 = 各档位笔数 / 已评分笔数   （分母不含 nil）
```

**为什么不用五颗星**：星星是连续刻度，逼用户做"3 星还是 4 星"的无意义精细区分，最终 80% 落在 4 星、20% 落在 1 星，中间三档作废；而且 iOS 里五颗星已经被 App Store 占据语义，会被理解成"给商户打分"。

### 9.14 余额调整与认领（v2.1 新增）

**场景**：账户实际余额和 App 里显示的对不上（忘了记一笔、现金进出没记）。

**核心原则：调整不是"改余额"，是生成一条"待认领的支出"。**

用户点「修改余额」并输入真实值，系统生成一条 `Transaction`：

```
kind   = .adjustment
amount = 差值（负数表示少了钱）
date   = 今天（发现问题的那天）
category = nil
grade  = nil
note   = "余额调整"
```

新余额 = 旧余额 + 差值。因为这条记录本身就在流水里，所以 `9.11` 的余额公式依然闭合，不需要任何特殊处理。

**认领（找到了这笔钱的来源）**

用户在账户详情里看到这条调整，点「这是哪笔」，补上分类、改日期，然后 `kind` 从 `.adjustment` 改成 `.expense`。

**关键：金额永远不变，只改类型和日期。**

于是余额自动保持正确，不需要把差值"退回去再扣一次"——那是最容易写出 bug 的做法。

> **实现状态补录（2026-11-13）**：本节描述的机制**代码尚未实现**。现状是 `LedgerService.flow(.adjustment)` 返回 `.zero`、`EntryViewModel.save` 的 `.adjustment` 分支是 `break`、全库从未创建过一条该类型的流水；余额校准实际走 `adjustAccountBalance`（改 `initialBalance` 再重算），不建流水。
>
> 2026-11-13 用户定案：**银行加进「本期应还」的利息/违约金也走 `.adjustment`**（不新增 `TransactionKind`）。因此在实现利息入口时一并启用本节机制——`flow` 改为返回 `(from: −amount, to: 0)`、`save` 真 insert、`countsAsExpense` 保持 `false`（本来就只有 `.expense` 为 true）。启用后本节与利息入口共用同一类型：都是「没有消费、但余额变了」，区别只在认领后 `.expense` 的认领动作。

| 操作 | 余额 | 当月支出 | 流水展示 |
|---|---|---|---|
| 生成调整 −120 | 减少 120 | 不变 | 「待认领差额 −120」 |
| 认领为支出 | **不变** | **+120** | 变成「购物 −120」，落在新日期那天 |
| 退回未认领 | 不变 | −120（回到 0） | 恢复成「待认领差额」 |

**只找到一部分（拆分认领）**：差额 120，实际那笔只有 100。

**做法是「拆成两条」，不是「改金额」**——一旦允许改金额，余额等式就会破：

```
原记录 −120  →  改为 −100 并转成 expense（补分类、补日期）
新建一条     →  −20 的 adjustment，继续挂着待认领
```

两笔合起来仍是 −120，余额不变，支出 +100。v1 可以先只做整笔认领：金额不等时自动按上面拆两条，逻辑一样，只是省掉一个输入框。

**跨月认领**：如果差额来自上月消费，认领时改日期到上月，那么**上月支出增加、本月不变**。必须给一句提示，否则用户会以为操作没生效。

**`.adjustment` 的统计规则**（与 9.1 一致）：不计入消费、不计入收入、不计入本月要还。它只影响账户余额。

### R2 三条边界

**一、抄骨架，不抄差异点。**
可抄：分组、行高、流程、键盘、图标位置。
不可抄：Fluent 3D Emoji 的用法、「还款不计支出」的视觉表达。这两样是这个 App 唯一的辨识度。

**二、市面对「还款关联到具体某一期账单」几乎没有实现。**
钱迹、Moze、MoneyWiz 都有转账类型，能做到「还款不计支出」。但都不关心这笔还款还的是 8 月账单还是 9 月账单。这一块必须自己写。

**三、市面的通用模型是「一个负债账户一个余额」，会算错。**
招行信用卡有 3 笔分期同时在读，共用一个额度，各有各的还款日。必须用 `Installment` 序列而非单一余额建模。这块必须自己写。

1. 任何一个界面，先问「哪个成熟 App 已经把它做到 90 分」，有就照抄
2. 只在两处做自己的设计：Emoji 呈现方式、还款与账单的对应关系
3. 不为了「看起来不一样」而改变交互习惯
